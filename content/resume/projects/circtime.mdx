## Overview

An experimental, AI-assisted topology and uptime visualization built as a companion to my long-running [self-hosted infrastructure project](/projects/web-development-personal-website/), not yet a production monitor.

## Highlights

- Built an AI-assisted React and TypeScript prototype to test a concentric, dependency-aware view of my hybrid-cloud topology, with human-in-the-loop design, review, and debugging.
- Added YAML-driven HTTP and TCP monitoring, degraded-state analysis, DNS discovery, an SVG uptime radar, a Three.js history view, and up to one year of retained history.
- Deployed the experiment through GitHub Actions and GitHub Pages, while keeping my established Uptime service as the production monitor until the post-migration configuration is corrected and validated.

## Project narrative

### Situation

My hybrid-cloud environment spans VPS hosts, a NAS, GPU infrastructure, DNS and routing layers, and many self-hosted services. I had already operated this environment for years and used an established Uptime service for production monitoring. After proactively migrating the root network node from a three-year-old CentOS server to Ubuntu—not because of a detected attack, but to reduce security-maintenance friction and work with the `apt` and `dpkg` tooling I know better—I wanted to explore a different way to see the system.

### Task

Test whether a concentric visualization could communicate infrastructure, service, and network dependencies more clearly than a flat status list. The experiment should be useful for my own environment first, reusable by other self-hosters later, and inexpensive to deploy without a dedicated monitoring backend.

### Action

I created an AI-assisted initial prototype and remained the human in the loop for the product idea, implementation direction, testing, and debugging. The React and TypeScript application combines an SVG concentric uptime radar with a Three.js history view. A single YAML configuration defines infrastructure, services, network nodes, dependencies, request thresholds, and retention. GitHub Actions performs HTTP and TCP checks every 15 minutes, keeps compressed history on a state branch, and deploys the static dashboard to GitHub Pages. I also added degraded-state diagnosis and experimental DNS and certificate-transparency discovery to help draft topology configurations.

### Result

The experiment is deployed and the monitoring workflow runs, but it is not yet production-ready. Its private configuration was created before the CentOS-to-Ubuntu migration and still checks some incorrect addresses and ports, so the earlier count of 67 configured nodes is not a validated description of the current infrastructure. It has improved how I think about topology visualization, but it has not yet detected a concrete incident or replaced the existing Uptime deployment. I am still correcting the configuration and deciding on the final public URL.

## Relationship to the self-hosted platform

circtime is a short continuation of [Web Development & Personal Website](/projects/web-development-personal-website/), not a separate production platform. It is best read as an appendix showing how I prototype a new operational idea, evaluate it honestly, and keep the proven service in place until the replacement is validated.
